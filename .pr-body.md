Six gaps found during a real refactor of the Flowmaatik domain layer —
eliminating `shared/` across seven entities. archwarden 0.4.0 reported the
problem correctly and helped with none of the diagnosis or the work.

Every feature is validated by running the binary against that repository
(3778 files, no `node_modules` installed), not against a fixture.

## The one that was not asked for, and blocks two that were

**Workspace packages resolved without `node_modules`** (decision 15).

A monorepo imports itself by package name. Node answers that by looking in
`node_modules`, and so does `oxc_resolver`. On a checkout that has not run an
install, that half of the graph resolves to nothing — measured: **5481 imports
by package name against 5690 relative ones**.

What makes it a bug rather than a limitation is that nothing said so. An
`import-boundary` rule over those edges reports nothing, which reads exactly
like a boundary that is satisfied.

The map is built from every `package.json` with a `name` and the `exports`
patterns that say where its subpaths land, handed to `oxc_resolver` as
**`fallback`** — consulted only after normal resolution fails, so a repository
that *has* installed its dependencies resolves exactly as before. No YAML
parser.

⚠️ **Behaviour change.** A project with an `import-boundary` rule over an
aliased edge will see findings on its first 0.5.0 run that 0.4.0 never
reported. That is the bug being fixed; a baseline is the answer if the debt is
not being paid today.

## `impact --apply`, and batch sources

Moves with `git mv` and rewrites every specifier that named the file —
including the ones written by package name, which is the half an editor cannot
do.

```bash
archwarden impact 'packages/domain/src/*/shared' --to '../calcs' --apply
```

On the reference repository: **15 files moved, 29 specifiers rewritten across
24 files, 15 renames recorded by git, zero imports left pointing at the old
location**, and `domain-entity-shape` down from 9 warnings to 2. The three
errors that remain are real, and the dry run announced them as "rules that
would start applying".

The five cases the rewriter has to get right, all verified: package-alias
imports, relative intra-entity imports, the moved file's own relative imports
(`../../calcs/validate-tag` → `./validate-tag`), the spec sibling travelling
along and following a rename, and a rename mid-move. **The exported symbol is
deliberately not renamed**, and the output says so.

Everything is computed and validated before a byte is written, so every refusal
is total. A dirty working tree is refused because git is the undo. A dynamic
import naming no module is the only refusal `--force` covers.

See decision 16 for why this is not `--fix`: **archwarden carries out the move
you described and never decides what to move.**

Two things the real repository caught that a fixture would not:
- `--to` was measured from each file's own directory, so
  `feature/shared/consts/x.ts` landed *inside* the folder being emptied.
- `git mv` left the emptied source directory behind — not cosmetic, since
  `structure` rules are about directories and all nine `shared` warnings
  survived a move of every file in them.

## `no-passthrough`

A file whose whole content forwards another module. Three shapes: re-export,
alias, one-line wrapper. Found **four** on the reference repository with
defaults and **zero false positives**, including two nobody had noticed.

A barrel file is the re-export case, so "no barrel files" — a line many
projects carry in a `CLAUDE.md` with no enforcement at all — is
`forms: ["reexport"]` with `allow_package_entrypoints: false`.

`allow_partial: false` also reports a file forwarding some exports while
declaring others, naming which. On the same repository, 4 findings became 26 —
both true, answering different questions, which is why it is a flag.

## `archwarden orphans`

Per folder: who imports its files, from inside the module, from outside, or
nobody. Answers "does this folder have a reason to exist?".

Specs are left out of the graph both ways. As *importers* they are the
distorting half: a file's own spec sits in the same module, so every file with
a spec reads as used from inside and outside at once. That turned six `shared/`
folders — every one used only from other modules — into six marked "both".

## `spec-pair`'s `skip_type_only`

A file whose exports are all `type`/`interface` has nothing a test can call.
Control on the reference repository: with `ignore_files` emptied and the flag
off, **5 errors** — exactly the five hand-maintained entries. With the flag on,
**none**.

## `--root`

`--config` answered both "where are the rules" and "what are they about", so a
config outside the repository walked its own directory, found no TypeScript and
reported a clean run — exit 0, the one wrong answer a reader takes as good
news. Now exit 2, naming the flag that fixes it. The refusal is narrow: an
empty root you are standing in is still checked.
